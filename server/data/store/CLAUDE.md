# Market data store

Owner of all persisted market data. Submits requests to data-ingest over gRPC (`Submit`) and receives each attempt's result on its own `StoreService.DeliverAttempt` (the push path), writes it to Postgres, and serves it over `/store/...`, `/internal/asset-data/...` and, to the web UI, the `/ui/v1/...` routes as protobuf canonical JSON (reads open; the dataset and panel writes behind the instance secret). Tables (every one is created by the single baseline revision `5d9a3c7e1b84`, see Migration safety): `store_dataset_entry` (its nullable `collect` column is the collecting intent, below; its nullable `stopped_cause` says why the store stopped it), `stock_market_activity`, `ingest_run`, `dataset_read`, `dataset_read_daily`, `dataset_override_log`, `dataset_deletion`, `ingest_request` (the durable request record, one row per request, written before it is sent; id is the request id) and `ingest_instance` (the instance marker), `corporate_action` (raw corporate-action observations), and `asset_list_snapshot`, `asset_list_row` and `asset_list_event` (dated raw asset lists and the events derived from them), and the five append-only panel tables `panel`, `panel_settings_version`, `panel_source_settings_version`, `panel_pass` and `panel_member_transition` (models in `app/database/models/panel.py`; the schema also has the nullable `dataset_override_log.new_value` and the index `ix_ingest_request_source_created_at`; no policy default in the schema, no foreign key to datasets or requests, `panel_pass.finished_at` and `counts` are the one write-once exception). `ingest_run` is also the attempt row of a reported attempt: its nullable `attempt_no`, `instance_id`, `quota_key`, `verdict`, `vendor_*` and `vendor_asset_id` columns, and a partial unique index on `(request_id, attempt_no)` where both are set, which an idempotent redelivery upsert must name with its `WHERE` (`request_id IS NOT NULL AND attempt_no IS NOT NULL`). No foreign key anywhere on these: runs outlive requests, requests outlive datasets.

## Architecture reference

`bd list -t arch_index --all` — child of `trader_joe system` (tj-mtwvnu). Design diagram: `docs/img/design.jpg`.

## Tech stack

Python 3.12, FastAPI, SQLAlchemy 2.0 async, asyncpg, Alembic, Postgres, `grpc.aio` (client of data-ingest's `Submit`, server of `StoreService`)

## Key invariants

Sole owner of persisted market data. Every write goes through a repository; no raw SQL in routers. The schema starts from ONE baseline revision (`5d9a3c7e1b84`, the alpha baseline: no parent, no downgrade, see Migration safety below); nothing applies migrations on start: run `make migrate` after every deploy (it follows the running stack, dev, test or prod). After the alpha, migrations are additive and forward-only again, held by `make lint-migrations`. No downgrade is a recovery path: recovery is a restore of the pre-migrate dump. The `collect` column is read by the catalog, the refresh and the writes, so a database that is not at head is not a state to run in.

**data_store runs ONE process: one uvicorn worker.** Six things are correct only because of it:

- the startup sweep of `RUNNING` ingest runs (`sweep_interrupted_runs` in `app/ingest/run_recording.py`, `fail_interrupted_runs` in `app/database/crud/ingest_run.py`) marks every `RUNNING` row `FAILED` / `INTERRUPTED`; a second worker starting would fail the run the first is executing;
- the events hub (`app/events.py`) lives in process memory, so an event reaches only the clients connected to the worker that published it;
- the usage buffer and the per-dataset-per-day id cap (`app/usage_recorder.py`): reads wait in this process's memory until a flush, and the 32-id cap is applied at flush against the stored ids, so two workers would each hold part of a day's reads and could together exceed the cap;
- the DAILY refresh loop (below): each worker would run its own pass and request the same missing tails. No cross-process lock exists; a Postgres advisory lock was considered for the scheduler and is not used: it is redundant while there is one worker, and it would be needed with two;
- the expiry reaper pass and its `ReaperPendingChanged` change detection (below): the previous pass's pending ids live in process memory, so a second worker would compare against its own copy and could announce a change that did not happen;
- the instance watcher (`app/ingest/instance_watch.py`, which re-sends pending requests and re-submits those a superseded ingest instance held) assumes the same. The end-state scheduler decision `tj-pd41mt` (a planner with admission) is still proposed; what is built of ingest's side is the queue, ready-by check, pacing and acknowledged retry in [`docs/scheduler.md`](../../../docs/scheduler.md).

`docker-compose.yaml` pins `SERVICE_WORKERS=1` as a literal in `environment:`, which outranks the operator's env file. A second worker would need all of these first:

- Postgres `LISTEN`/`NOTIFY`, so each worker republishes into its own events hub;
- a startup sweep keyed by process rather than by "every `RUNNING` row";
- a lock or leader election for the DAILY refresh and for the reaper, so two workers do not both run them;
- the reaper's change detection moved out of process memory;
- the usage buffer and the per-dataset-per-day id cap made safe across workers.

## Migration safety

The procedure is in the root README (Database migrations); the facts a store agent needs:

| Concern | Fact |
|---|---|
| Where the revisions live | In the data_store image (`/code/migrations`), not mounted from the checkout. An edited or new revision reaches a stack only after `make dev-build`, `make test-build` or `make prod-build`; `make migrate` against an older image runs that image's set and refuses an image with none. Both service source digests cover the revisions, so ingest's image goes stale too |
| Pre-migrate dump | `run_migrations.sh` dumps before any schema-moving command (`upgrade`, `downgrade`, `stamp`): `pg_dump` custom format, `.partial` then read back with `pg_restore --list` then renamed, mode 600, into `MIGRATE_BACKUP_DIR` (default: the backups folder beside the database's data directory, that is the parent of the host directory bind-mounted at the running postgres's `/var/lib/postgresql/data` plus `/backups`, read with `docker inspect`, so it follows whatever `DATA_DIR` the stack was started with; if there is not exactly one bind mount there with an absolute source, or the inspect fails, and `MIGRATE_BACKUP_DIR` is unset, the migrate is refused before alembic, so a postgres on a named volume needs `MIGRATE_BACKUP_DIR`; the mount source is a path on the Docker daemon's host, so run `make migrate` on that host), on the database's host, path printed on the dump line, never pruned. A failed dump refuses the migrate; there is no override |
| Production label | On the production definition a non-empty `DEPLOYMENT_LABEL` refuses the migrate. Dev and test are not asserted |
| Restore and rehearse | `make migrate-restore DUMP=<file>` and `make migrate-rehearse DUMP=<file>` (`restore_dump.sh`, `rehearse_migration.sh`) set `SYSTEM_TEST_DISPOSABLE_DB=1` in the recipe and refuse unless the running postgres is the `trader_joe_dev` test stack (`make system-launch`). Rehearsal prints `REHEARSAL OK` only at `(head)` and with data_store not unhealthy; the health line is the container's last status, with no restart, and the revisions applied are the running test image's (the checkout's only after `make test-build`) |
| Production recovery | A manual `pg_restore` of the pre-migrate dump; no script restores into production |
| No backup target | There is no standalone backup make target; `make migrate` takes the dump. Scheduled backups are `tj-oxwlda`; CI's `make migrate` takes the dump too, the agent-stack migrate tool (dev and test only) takes none |
| Lint gate | `make lint-migrations` (in `make lint`; `tools/migration_lint`) refuses non-additive store revisions outside `downgrade()` unless a line `# additive-exception: <bead-id>` marks them (the baseline is create-only and passes unmarked; no revision in the tree carries a marker, and the marker machinery stays for later revisions). It is a text-level check against honest non-additive changes, not a SQL parser: it refuses any raw SQL containing a dollar-quote delimiter (`$$` or `$tag$`; a positional parameter such as `$1` is not one), since it does not read dollar quoting; it does not understand `E'...'` backslash escapes or nested block comments, and can fail open on either; and it refuses an unterminated comment or quote and raw SQL it cannot resolve |

### The alpha baseline

The alpha is the first release whose data persists, and it starts from one revision. `server/data/store/migrations/versions` holds exactly one file, `5d9a3c7e1b84_alpha_baseline.py`: `down_revision` is `None`, it creates every table, column, type, enum, index, unique constraint, CHECK and foreign key of the models as they stand (the enum label lists are literals in the file, not read from imported code), and its `downgrade()` raises `RuntimeError`. The sixteen revisions before it are gone, and so is a one-off data-repair archive table one of them created, which the baseline does not carry.

- **To start, drop the database and run `make migrate`.** There is no upgrade path from a schema before the baseline: the repository supports none. A database stamped with an earlier revision id fails at `make migrate` with "Can't locate revision", because the baseline's id is new.
- **The baseline was edited in place on 2026-11-07, keeping its id** (the two panel source rates became nullable, with new CHECKs), and again on 2026-11-10 (`panel_settings_version.include_otc`, boolean NOT NULL, no default). A database already at `5d9a3c7e1b84` is not upgraded by `make migrate` (it is a no-op) and keeps the old columns, so every stack, dev included, must be dropped and migrated again; `make migrate-check` shows the drift.
- **There is no downgrade.** Recovery is a restore of the pre-migrate dump `make migrate` takes (Migration safety table above). Datasets exported before the baseline (`output/dev_seed/<old revision>/`) cannot be loaded into it; request them again after the reset.
- **After the alpha, migrations are additive-only again**, held by `make lint-migrations` and the marker rule above. Whether data-carrying upgrade checks and release seeds return is decided when the first revision after the alpha is planned; until then there is no test of an old or invalid schema and no committed per-revision seed.

**The baseline gate.** The architect applies these at the gate of the baseline's work, and to any change to that file. A "no" on any item is CHANGES NEEDED.

| # | Check |
|---|---|
| B1 | One revision file, one head, `down_revision` `None`, a fresh id (none of the replaced ones), no branch label or dependency, no `additive-exception` marker (`test_alpha_baseline_revision.py`) |
| B2 | `downgrade()` raises `RuntimeError` before any operation |
| B3 | `make lint-migrations` passes it unmarked (`tools/migration_lint/tests/test_migration_lint.py`) |

Any other difference is listed and ruled, never accepted silently. It is recorded, not committed: the earlier chain no longer exists |
| B5 | The catalogue of `alembic upgrade head` from empty equals the catalogue of `metadata.create_all` on a second scratch database, green on Postgres (`tests/system/test_alpha_baseline_schema_pg.py`; it covers the CHECKs, enum labels and server defaults `alembic check` cannot see) |

**Deploy procedure.** Checked from the operator's transcript at the production sitting, not from the diff. (1) Before a production migrate: `make prod-build` from the reviewed SHA, and the production definition's `DEPLOYMENT_LABEL` is empty (non-empty refuses). (2) A production dump restored and rehearsed on the test stack after `make test-build` (`make migrate-restore` and `make migrate-rehearse DUMP=<file>`) printed `REHEARSAL OK`, then the stack was restarted and its health read. (3) The production `make migrate` printed its verified dump line, and the operator copied the dump off the host. (4) Rollback: code rollback across a migration boundary does not work, downgrade is not supported, and recovery is a manual `pg_restore` of that pre-migrate dump.

## Dataset health and completeness

Dataset health (recency and completeness are its two parts) is **computed on read and never stored**, by three pure modules (the clock and
the calendar are arguments) and composed with the queries in `app/dataset_catalog.py`. They
serve the `/ui/v1` routes. The modules depend one way, `app/trading_calendar.py` to `app/completeness.py` to
`app/health.py` to callers. The combined status enum is `DatasetHealthStatus` in `app/health.py`, mirrored by the proto enum of the same name (values `DATASET_HEALTH_STATUS_*`), and the proto message is `DatasetHealth` (`DatasetSummary.health`); the module that judges is `health`. There is still no coverage ledger: no `missing_ranges` query, no `range_agg`
subtraction, and the older read routes (`/store/...`, `/internal/asset-data/...`) say nothing about
completeness, so a short answer from them is not distinguishable from a complete one.

| Concern | Where it lives |
|---|---|
| Status per dataset (`FRESH`, `LATE`, `OVERDUE`, `COMPLETE`, `GAPS`, `RETIRED`; `RETIRED` means a DAILY or STREAM dataset with `collect` false, shown as Stopped) | `evaluate_dataset` in `app/health.py` returns a `DatasetHealth`; its `DatasetHealthStatus` is the combined status the proto and UI see. The DAILY and STREAM recency rules and `RETIRED` live there, with `HealthConfig`; a STATIC dataset's status is mapped from `assess_completeness` in `app/completeness.py` (`COMPLETE`, `GAPS`) |
| Trading calendar | `app/trading_calendar.py`: one per data source (`SOURCE_CALENDARS`, offline `exchange_calendars`, via `calendar_for_source`; the `TradingCalendar` protocol and `ExchangeCalendarAdapter`), with `session_of`, `local_midnight` and `require_aware`; a source with none has no computed health |
| Status vocabulary the UI filters by | `StatusGroup` in `app/dataset_catalog.py`: healthy, late, failed, retired |
| Catalog listing, facets, bar paging | `app/dataset_catalog.py` over `app/database/crud/stock/dataset_catalog.py`; keyset cursors, opaque, bound to their sort |
| Bar page index (`GET /ui/v1/datasets/{id}/bar-pages`, the Viewer's paging) | `bar_page_index` in `app/dataset_catalog.py`, `read_bar_page_starts` in `app/database/crud/stock/dataset_catalog.py` |
| Coverage strip (`GET /ui/v1/datasets/{id}/coverage`): buckets and gap windows | `coverage_buckets` and `gap_intervals` in `app/completeness.py` and `local_midnight` in `app/trading_calendar.py`, composed by `dataset_coverage` in `app/dataset_catalog.py` |

Things that bite:

- **Completeness counts sessions; coverage is by period.** A session is covered when a bar covers its
  period: the session itself for 1-minute to 1-day, the Monday-Sunday week for 1-week, the calendar month
  for 1-month, in the trading calendar's time zone, whichever day of the period the vendor stamps. A period
  is expected when its first day's local midnight is in `[start, end)`, it has ended (its last session has
  closed) and it holds a session (`judged` in `app/completeness.py`), so the sessions of a partial first period
  are not expected. Gap counts and gap windows count only the expected sessions inside `[start, end)`: `_in_range`
  clips them, so a week or month whose only sessions fall past the range end owes nothing.
  A DAILY 1-week or 1-month dataset is FRESH when its last bar's period is at least the last ended period.
- **A bar is FINAL only if it was written at or after its period closed** (tj-grna9p.167). A vendor's bar fetched during an
  open period is part-way, so a DAILY dataset whose newest bar is of the expected period and was written before that
  period closed and settled is provisional: while it stays so, the dataset reads LATE, not FRESH, until the next session after the expected period opens, then OVERDUE (a failure). The refresh re-fetches FROM THAT BAR INCLUSIVELY; the bar upsert sets
  `updated_at` explicitly (`ON CONFLICT` skips `onupdate`), so the rewrite after the close makes it final and the dataset FRESH. The rule is `last_bar_is_provisional` in `app/health.py`. The close is
  the calendar's SESSION close plus the settle margin (`bar_period_close` in `app/health.py`), for every granularity up to 1day (an intraday bar is final only when written at or after its SESSION's close plus the margin, not its own period end); for 1week and 1month it is the close of the period's last session plus the margin. The margin is `DAILY_REFRESH_SETTLE_MINUTES` (`settle_margin_from_env`, default 30), the same value that paces the refresh. A STATIC dataset is unchanged. The write time is
  Postgres `now()`, the transaction start. **The write time is a lower bound on serve time.** The fetch transaction opens, with the own-overlap check, BEFORE the vendor request (`store_market_activity_worker`), and `updated_at` is `now()`, the transaction start. A bar is written before its stamp when `written_at < timestamp` (`written_before_its_stamp` in `app/health.py`, strict: equality is not before), the one predicate health and the refresh share. **A newest real bar written before its stamp is judged AT ITS WRITE TIME** (`_daily`, decision tj-7zjov1.120 addendum 1): the ordinary rule (period, provisional test, first missed period, deadline) runs on the write time, because the bar proves the dataset fetched through that instant and no further. A live 1min fetch whose last bar is stamped seconds after the transaction start therefore reads FRESH after the close, and a bar stamped a week ahead is owed at the first close after it was written (LATE after that close, OVERDUE from the next open, unless rewritten).
- **A bar belongs to the session whose local date, in the calendar's time zone, its timestamp falls on.**
- **Ranges are half-open `[start, end)`** in the store, the bar reads and the overlap check: a bar at
  `end` is in the next range, and ranges that only touch do not collide. A declared `end` not after
  `start` is refused at the edge.
- **Filtering on status needs health for every matching dataset**, not one page, so that a facet count
  equals the filtered list's total. A request with no status filter evaluates the page only. The
  request's statement count is constant, never one per dataset.
- **Two gap counts, in different units.** `CoverageStrip.gap_count` counts gap *intervals* (maximal runs of missing completed sessions); `DatasetHealth.gap_count` counts missing *sessions*. For a `STATIC` dataset the sessions of all gaps add up to the health count. The strip lists at most 500 gaps (`MAX_COVERAGE_GAPS`), so `gap_count` may exceed the list.
- **A gap window is whole sessions**: from the local midnight of its first session to the local midnight after its last, so it can start before or end after the dataset's range by the part of a session. Buckets and gaps both count only the sessions inside the range: a 1week or 1month period straddling the range end still decides covered or not, but only its in-range sessions are reported missing, so `DatasetHealth.gap_count` equals the buckets' expected sessions without a bar. A coverage read costs two statements and records no usage. With no trading calendar covering the dataset it is a 422, never an empty strip, which would read as no gaps.
- **The page index is fixed blocks counted back from the newest bar**, so the earliest page, not the newest, takes the remainder and overlaps its neighbour. Offsets are `[0 if r > 0], r, r + size, ..., N - size` with r = N mod size; `overlap` is the client's look-ahead and never moves one. It is two statements (the entry, then one read that scans the window twice: a count and the ranks), about 0.7 s at 2.4M bars, and it is a snapshot of the window it was read for.
- **Two maximums, kept apart.** `MAX_BAR_LIMIT` (the UI bars read) is 50,000 and `MAX_PAGE_INDEX_SIZE` (the page index `size`) is 1,000. Raising the first does not raise the second.
- **Expiry is a DELETION date only** (decision `tj-hhy3dk`). None means the dataset is never deleted by the reaper. Setting or clearing one retires and resumes nothing, for every update type, and a past expiry does not change health. A repeat `POST /store` still sets expiry from its body, so omitting it clears a stored one.
- **Collect is the collecting intent** (`store_dataset_entry.collect`, nullable bool). A `DAILY` or `STREAM` row holds true (collecting) or false (Stopped, read as `RETIRED` on the wire: the enum names are kept); a `STATIC` row holds NULL, enforced by a CHECK, and has no intent. `DatasetSummary.collecting` is `is_collecting` in `app/dataset_catalog.py`: the intent for a subscription (NULL reads as true), and for a STATIC dataset whether its latest run is `RUNNING` (derived, never stored). `is_retired` (same module) is collect false on a subscription, and health, the status group, the refresh and `lock_active_entry` all judge by it. **`stopped_cause`** (nullable string, `DatasetStopCause`) says the STORE set collect false: the stop rule (Delivery intake, `VENDOR_ASSET_CHANGED`) and the panel manager (`stop_collecting`, `PANEL_MEMBER_LEFT`) are its two writers, NULL means the operator or nobody stopped it. `operator_set_collecting` with collect true and a `POST /store` repeat carrying an explicit collect true clear it in the same UPDATE (the CHECK refuses a cause on a collecting row); collect false from PATCH or POST, and an omitted collect, leave it as stored, and an operator stop never sets it. The reaper ignores it.
- **`POST /store` carries an optional `collect`** (`StoreAssetDatasetBody`; a 422 on a `STATIC` request). On create an omitted `collect` is true for a subscription. On a repeat an omitted `collect` LEAVES THE STORED VALUE UNCHANGED and only an explicit one changes it, so an SDK retry of its original body cannot undo an operator's Stop. This differs from expiry on purpose: collect is the operator's intent, expiry the requester's own deletion date.

## Collection record and live events

**Since the push path (`tj-7zjov1.28`, P35) a request is recorded as an `ingest_request` row, written before it is sent, and each reported attempt is one `ingest_run` row written by the delivery intake in the delivery transaction** (see Delivery intake). `POST /store` and the DAILY loop no longer open a `RUNNING` row: `recorded_run` and the rest of `app/ingest/run_recording.py` below are the LEGACY record, kept (with the startup sweep, which fails any `RUNNING` row an earlier release left) until a follow-up removes them. Running state reads OPEN REQUESTS (`running_dataset_ids`: PENDING, QUEUED or NOT_DELIVERED with a dataset id) as well as legacy `RUNNING` rows.

Every fetch the store drove before then (`POST /store`) was recorded as one `ingest_run` row, by the run recorder
(`app/ingest/run_recording.py`). The row is what the UI's run history, `last_run` and Running state read.
It is separate from the entry and its bars, and is not part of the fetch's transaction.

| Concern | Where it lives |
|---|---|
| The table: one row per store-driven fetch; no foreign key to the dataset, so runs outlive a deletion | `app/database/models/ingest_run.py` |
| Reads and writes of the table (start, acknowledge, finish, sweep, runs list, latest run per dataset, running ids) | `app/database/crud/ingest_run.py` |
| The recorder: a `RUNNING` row before the stream opens, the dataset id at ingest's acknowledgement, a terminal row at the end | `recorded_run` in `app/ingest/run_recording.py` |
| The events hub: bounded queue per client, drop on overflow | `app/events.py` |
| The socket `WS /ui/v1/events`, one `UiEvent` text frame per event | `routers/data_store/ui_events.py`, mapped in `routers/data_store/ui_mapping.py` |
| Runs list, coverage strip, Running filter and facet | `run_page`, `dataset_coverage`, `list_page` in `app/dataset_catalog.py` |

- **A run's states** are `RUNNING`, `SUCCEEDED` (bars written), `EMPTY` (the vendor answered and held none; not a failure) and `FAILED`. A legacy-recorder `FAILED` row carries the typed `(domain, reason)`, the detail and the error id. A push-path attempt row (`DeliveryIntake`) carries `error_message` (the trailer's detail) and, when the `FAILED` trailer's `reason` is set (ingest sets it on every typed failure), `error_domain` = the vocabulary's `ERROR_DOMAIN` and `error_reason` = that `Reason`; a trailer with no reason (an untyped failure, a crash path) leaves both NULL, never derived from `error_class`, and a non-`FAILED` trailer never writes them. Rows written before this are not backfilled. `INTERRUPTED` (the startup sweep's) and `VENDOR_ASSET_CHANGED` (the stop rule's, `error_domain` NULL) are run-record markers, not members of the error vocabulary, and never reach problem+json.
- **Legacy recorder (`recorded_run`, which no path calls now): each write is its own transaction on its own session** (`own_session`), so the `RUNNING` row is visible while the fetch is in flight and a rolled-back fetch still leaves its `FAILED` row.
- **Legacy recorder: the record is best effort.** A failure to write it is logged and the fetch carries on unrecorded; the cost is a missing or stuck row, which the startup sweep bounds. The exception of the fetch itself propagates unchanged.
- **`dataset_id` is NULL on an attempt row that names no dataset**: a clamp query, or a POST's attempt that failed before any delivery created the entry (the first delivered attempt writes it, below).
- **The actor** is the request body's `owner`. It is a `SensitiveString` and is never logged.
- **Events are notifications, not data.** Publishers call `publish()` strictly after their own commit. Published today: `IngestRunChanged`, ONE per reported attempt, after the delivery that wrote its `ingest_run` row commits (`deliver` in `app/ingest/delivery_intake.py`; no `RUNNING` frame: the legacy start, acknowledgement and finish frames are gone with the legacy recorder's use on the POST path). A POST therefore announces the name_change clamp's corporate-actions attempt first (a frame labelled with the symbol alone, `EMPTY` when the vendor holds no name change), then one frame per bars attempt (`SUCCEEDED` naming the dataset and the request, or `FAILED` per attempt, trigger `REQUEST` then `RETRY`), then `DatasetChanged` `UPDATED`; a refused feed (`FEED_NOT_AVAILABLE`) writes no attempt row and announces the clamp's frame only (pinned by `tests/system/test_ws_ui_events.py`). `DatasetChanged`: `UPDATED` (after the delivery that resolved the dataset, a POST's or a DAILY refresh's, that does not flip collect, and after `PATCH .../expiry`), `RETIRED` / `RESUMED` (a collect flip to false / true, from `PATCH .../collecting` or from a delivery of a POST that flips it; `RETIRED` also when the stop rule or the panel manager stops a dataset; a collecting PATCH that leaves the stored value as it was publishes nothing, and a `POST /store` that does is `UPDATED`) and `DELETED`. `CREATED` is never published: a new dataset arrives as `UPDATED`, because the upsert does not tell the two apart. `ReaperPendingChanged` is published by the expiry reaper (below). `RequestChanged` is typed in `app/events.py` and in `ui/v1/events.proto` and has no publisher.
- **An event is published after the commit that wrote what it names**, so a reload by id finds it (the legacy acknowledgement frame, which could name an uncommitted entry, is no longer published). REST is the truth.
- **A slow client is dropped, never waited for.** Its queue is bounded (`EVENTS_CLIENT_QUEUE_SIZE`); when it fills the hub drops the client and the router closes the socket with 1013. The client reloads over REST on reconnect.

## Delivery intake (the result path, `StoreService`)

Ingest pushes every attempt to the store's gRPC server (`app/grpc_host.py`, entered at the end of the lifespan, bound at `APP_INTERNAL_GRPC_HOST:APP_INTERNAL_GRPC_PORT`, no default). `DeliveryIntake` (`app/ingest/delivery_intake.py`) is the handler behind `common/rpc/store.py`; its statements are in `app/database/crud/ingest_delivery.py`.

- **One transaction per delivered attempt, answered only after the commit**: lock the request row `FOR UPDATE`, answer a duplicate from the stored row, check the cross-field rules, write the data (the kind's arm), the attempt row (`ingest_run`, spend included, failed attempts too), then the request's durable count, spend and state. Any failure rolls all of it back and ingest redelivers the same attempt number.
- **Idempotent on `(request_id, attempt_no)`**: the lock serialises deliveries of one request; the partial unique index is the `ON CONFLICT` arbiter (named with its `WHERE`). A duplicate writes nothing and repeats the stored verdict with the request's count. EXPIRED and EXHAUSTED reports have no attempt row: a finished request is their stored answer. The same number from another instance is dropped with FINAL when that instance is superseded and refused (INVALID_REQUEST) when it is the live one.
- **The instance sighting commits first, on its own** (`note_instance_seen`); a report from a superseded instance is still written and answered FINAL, and finishes the request only when conclusive (a success, a permanent refusal).
- **Verdict**: FINAL on a success, a PERMANENT refusal, `last_attempt`, EXPIRED, EXHAUSTED, a superseded instance or an already finished request; else CONTINUE. EXPIRED and EXHAUSTED write the request FAILED (cause `EXPIRED` / `ATTEMPTS_EXHAUSTED`), no attempt row, the count unchanged, no spend.
- **Arms are separate functions** (`write_bars`, `write_asset_list`, `write_corporate_actions` in `ARMS`), called inside the transaction. An arm that is missing refuses its payload INVALID_REQUEST, never acknowledges it unwritten (an asset list cannot be fetched again). The corporate-actions arm (P18) and the asset-list arm (P17) are below.
- **Spend rules**: a SUCCEEDED or FAILED report must name a quota key, and a SUCCEEDED one must carry vendor stats (both refused INVALID_REQUEST). A FAILED report with no stats is accepted (the attempt runner's crash path sends one) with one WARNING; its vendor columns stay NULL (spend unknown, never zero), the request sums add 0 and `ingest_request.spend_unknown_attempts` adds 1.
- **No orphan bars**: bars carry a foreign key to their dataset with `ON DELETE CASCADE`, so the database never keeps a bar whose entry is gone, and that key is the backstop. The bars arm still locks the dataset entry `FOR UPDATE` first (`lock_active_dataset_entry`, the row the reaper and the operator's delete lock) so that a delivery for a deleted or stopped entry is DROPPED cleanly instead of surfacing a foreign-key violation, so it serialises with the delete, the Stop and the reaper, and so the drop rule has one place to judge under the lock.
- **The bars arm writes the dataset entry on the first delivered attempt** (P35). A request with no `dataset_id` (a POST) has its entry upserted from the request row (owner = `client_label`, symbol, asset type, the one data type, source, granularity, update type, the requested window, `expiry`, `collect`, and `expiry_type`, the POST body's own declared value, never a guess) plus the header's resolved feed, and `ingest_request.dataset_id` is set, all in the delivery transaction; a zero-bar success creates it too. A NULL `expiry_type` on such a request is refused INVALID_REQUEST, never BULK. An exact repeat sets the expiry from the request and `collect` only when explicit, as POST /store always did, and a collect flip publishes `RETIRED` or `RESUMED`. The own-overlap refusal is the POST's, made before the request is written, and it is FEED-BLIND: `OverlapKey` is the identity minus `feed`, and the range-equality exclusion ignores it too, while `feed` is identity. Current behaviour (owner ruling 2026-11-06 on `tj-7zjov1.351`, fix in backlog `tj-7zjov1.352`): one owner may hold a SIP and an IEX dataset for one symbol and granularity; an IEX request over a window that PARTLY overlaps an owned SIP dataset is a 409; an IDENTICAL window is accepted as a second dataset (`docs/API.md`, "What a create does"). The panel manager's creation uses the same check (cause `own_overlap`). The check is not repeated here, because a refusal inside this transaction would be redelivered for ever (a concurrent overlapping POST can therefore both land: accepted residual). A request that already has a `dataset_id` (the DAILY loop writes it) is a refresh: the entry is locked and judged first, only `updated_at` is written, and a GONE or STOPPED (collect false on a subscription) entry DROPS the delivery: nothing stored, the attempt row EMPTY, the request finished EMPTY with cause `DISCARDED`, answered FINAL.
- **A SUCCEEDED bars report must carry a served range** (rule (i) of `validate_report`, INVALID_REQUEST naming the rule): the waiter returns it from the attempt row. A duplicate delivery whose stored verdict was CONTINUE is answered FINAL once the request is no longer open (the stored row is unchanged), so a late redelivery of an earlier attempt cannot make ingest act on a stale CONTINUE.
- **The request path** (`app/ingest/data_action_request.py`): `POST /store` writes the request (trigger REQUEST, the body's `expiry`, `expiry_type`, `collect`, `ready_by` or none), submits it through `IngestSubmitClient`, notes the answering instance, marks the request QUEUED under it (never under a superseded instance: `mark_queued`), and `await_verdict` polls the REQUEST ROW until it is not open or the deadline (`STORE_VERDICT_DEADLINE_SECONDS`, default the 300 s fetch deadline), answering from the request's state and its finishing attempt row (bars written, served range), never from an answer ingest received. Failures: EXPIRED is DEADLINE (504), PERMANENT is VENDOR_REJECTED (422), exhausted attempts VENDOR_UNAVAILABLE (503), a refused feed FEED_NOT_AVAILABLE (422, the request FAILED PERMANENT); a request still open at the deadline answers the deadline error and keeps running (owner ruling R4, option a). A Submit call that fails leaves the request PENDING (watcher). The DAILY loop uses `submit_bars` with trigger SCHEDULE, `dataset_id` set, `ready_by` the next market open (`next_market_open`), no expiry, collect or expiry type, and does NOT wait.
- **The name_change clamp** (P51, `tj-7zjov1.146`, ADR `tj-26jt9w` addendum 19; no revision, no wire change). EVERY POST (a bars request with no dataset id) first writes, sends and awaits ONE corporate-actions request (trigger REQUEST, `new_corporate_actions_request`) for the symbol over `CALENDAR_START` to now, a window wide enough that the vendor's date filter cannot exclude a record. The clamp is read from EVERY stored `name_change` naming the symbol, whichever request delivered it (`name_changes_naming` in `crud/corporate_action.py`, the newest observation per vendor action id; `name_change_clamp` in `app/corporate_actions.py`): a candidate has `old_symbol` equal to the symbol and is dropped when a row with `new_symbol` equal to it has a strictly later process date (a rename and back); a record with no process date is ignored with one WARNING count. The latest remaining process date, at local midnight in the source's trading calendar (UTC midnight without one), applies only when after the body's start, and then REPLACES the body's start for the own-overlap key, `requested_start` and so the entry, every re-send and the DAILY refresh floor: the clamped start is the entry's identity, so a repeat clamps to the same start and extends the entry. A clamped start at or after `end` is INVALID_REQUEST naming the symbol and date, nothing sent for bars. FAIL CLOSED: a corporate-actions request that fails, expires or misses the deadline fails the POST with that error and no bars row is written; one verdict deadline covers both waits. The caller sees it in `served_range.start`, in the route message and in one INFO log line (symbol, both starts, both request ids). The DAILY loop and the watcher never clamp.
- **The instance watcher** (`app/ingest/instance_watch.py`, `run_periodic`, started in the lifespan): for BARS, ASSET_LIST and CORPORATE_ACTIONS rows (a POST's clamp query is re-sent like any request), re-sends PENDING requests older than 30 s, probes `Instance` each pass, and re-submits requests held by a SUPERSEDED instance (NOT_DELIVERED, and QUEUED under a superseded instance) flagged `recovered` with the durable attempt count read under the request lock, only once the instance was superseded for `DEFAULT_DELIVERY_DEADLINE_S` (60 s) plus a margin, so the old instance's last in-flight report has committed or is refused for ever. Kill switch `INSTANCE_WATCH_ENABLED`, dry run `INSTANCE_WATCH_DRY_RUN`.
- The same attempt number from another instance is logged at ERROR on both branches: P35 prevents it by waiting out the delivery deadline before it resubmits, so they are guards.
- **The push-path columns** (P34c, `tj-7zjov1.123`), all in the baseline: `ingest_run.served_start` / `served_end` (the SUCCEEDED trailer's served range, NULL on every other attempt row); `ingest_request.trigger` (the existing `ingest_run_trigger` type, nullable, NULL reads as REQUEST: the first attempt row takes it, every later one is RETRY), `expiry` and `collect` (the POST body's lifecycle fields; mapped by `NewIngestRequest` and `IngestRequestRecord`, written by `POST /store`, below), and `spend_unknown_attempts` (integer NOT NULL default 0: counted FAILED reports with no vendor stats; when non-zero the request's spend sums are a lower bound); and `store_dataset_entry.stopped_cause` (nullable string; NULL means the store did not stop it, whatever `collect` says) with the CHECK `ck_store_dataset_entry_stopped_cause_needs_stop` (`stopped_cause IS NULL OR collect IS FALSE`, so a collecting or STATIC row can never carry a cause). The stop rule (`tj-7zjov1.144`) is `stopped_cause`'s one writer and needed no revision. Attempt rows for non-bars requests landed with P18 (`tj-7zjov1.31`, below).
- **`ingest_request.expiry_type`** (P35r, `tj-7zjov1.153`): a nullable integer (`ExpiryType`'s value, as the entry's column stores it) with no default, NULL where the request carries none (the DAILY loop, an asset list, corporate actions), mapped by `NewIngestRequest` and `IngestRequestRecord` and written by `POST /store` (the body's value); P35 (`tj-7zjov1.28`) is its one writer. `trigger`, `expiry` and `collect` are written the same way (the DAILY loop writes trigger SCHEDULE).
- **`corporate_action` and five nullable `ingest_run` columns** (P18, `tj-7zjov1.31`). `corporate_action` is APPEND-ONLY, one row per observation, tied to no dataset and no listing (ADR `tj-26jt9w` addendum 12): vendor action id, type, the five vendor dates (ex, record, payable, process, effective), identifiers (JSONB), `raw_payload` bytes and their SHA-256 `payload_hash`, the delivering `request_id` and `attempt_no`, the `requesting_symbol`, the requested window, `as_of` (the trailer's, else the transaction start) and `received_at`. The unique index on `(source, vendor_action_id, payload_hash)` is the dedupe: the same id with the same bytes is the same observation and is kept once (nothing is written, nothing counted); the same id with other bytes is a vendor revision and is a new row with its own `as_of`. `write_corporate_actions` stores EVERY record a delivery carries: the requested window is a fetch parameter, never a filter. The attempt row of a corporate-actions request keeps the symbol it asked for and NULL `asset_type`, `data_type`, `granularity` and `update_type` (`asset_symbol`, `asset_type`, `data_type`, `granularity`, `update_type` are nullable now; `IngestRunRecord` fields are optional, the UI label drops what is absent, the DAILY refresh history reads only rows with a granularity). `bars_written` is bars only (0 for another kind), and `ingest_run.vendor_asset_id` is stored for a bars attempt only (NULL for another kind whatever the header carries). A SUCCEEDED corporate-actions report must carry a served range (rule (i)), stored on its attempt row.
- **The asset-list snapshot tables and `ingest_request.asset_list_status`** (P17, `tj-7zjov1.30`). THE REQUEST ROW NAMES ITS LIST (ADR `tj-26jt9w` addendum 17): `ingest_request.asset_list_status` is nullable, of the new Postgres enum `asset_list_status` (labels `active`, `inactive`, the values of `AssetListStatus`), and the CHECK `ck_ingest_request_asset_list_status`, `(kind = 'ASSET_LIST') = (asset_list_status IS NOT NULL)`, ties it to the kind both ways; `NewIngestRequest` refuses the same combinations in `__post_init__`, `new_asset_list_request` (`app/ingest/data_action_request.py`) writes the row and the ASSET_LIST branch of `submit_request_of` sends the same value as `AssetListRequest.status`; `open_asset_list_request_exists(db, source, status)` (`crud/ingest_request.py`) says whether one is in an open state. Three APPEND-ONLY tables (`app/database/models/asset_list.py`, statements in `crud/asset_list.py`, logic in `app/world_snapshot.py`), no foreign key: `asset_list_snapshot` (one dated header per delivered asset-list attempt, EMPTY ONES INCLUDED with `row_count` 0: source, asset type, the list, request id and attempt number (unique), `as_of` the snapshot instant), `asset_list_row` (one vendor asset exactly as served: vendor asset id, symbol, name, exchange, the vendor's `active` and `tradable` flags with NULL for "said nothing", and the raw payload bytes) and `asset_list_event` (see below). `write_asset_list` files EVERY delivery, empty or not, under the REQUEST's list only: the records' `active` flag never chooses it. A NULL list on the request (unreachable: the CHECK) is REFUSED INVALID_REQUEST, never defaulted to active (filing one list under the other would derive about 14,000 false vanished events). A record contradicting its list (active False on the active list, True on the inactive one) is stored raw, counted as a member and logged as ONE WARNING with the count; nothing is refused, because a refused asset list is redelivered for ever and lost at an ingest restart; an `active` of None is a member with no warning. The attempt row has every label column NULL and no served range (an asset list has no window; `asset_list` is not in `_SERVED_RANGE_KINDS`). EVENTS are derived by vendor asset id in the delivery transaction against the previous NON-EMPTY snapshot of the same `(source, list)` (the base; `newest_snapshot(..., include_empty=False)` is the newest-snapshot read, and the age P47's rule reads): `appeared` (an id new to the list), `vanished` (an id gone from it), `status_flip` (an id new to the list that an earlier snapshot of the OTHER list held; the event carries both symbols, so a delisting that renames on the same id is one flip). A vanished is ALWAYS reported for an id gone from the base (addendum 18): a move between lists is a vanished on the list it left plus a status_flip on the list it reached, in either arrival order. A LATE snapshot (its as_of not after the newest non-empty snapshot's of its list) is stored raw, derives no event and logs one WARNING. Each event names the id, the symbols as observed, and both instants (`as_of` this snapshot, `previous_as_of` the base, or for a flip the other-list snapshot that last held the id). An EMPTY snapshot derives NO event and is never a base, so a vendor glitch never reads as every listing vanishing; the FIRST non-empty snapshot of a list has no base and derives none. The snapshots of one `(source, list)` are serialised by a transaction advisory lock (`lock_list`), because two requests' locks do not order them. No rename or reuse events, no listing tables, no symbol ranges (addenda 12 to 17).
- Bars are written under `ingest_request.dataset_id`, which the first delivered attempt of a POST sets. The bars header's `vendor_asset_id` is stored as received, opaque, in `ingest_run.vendor_asset_id` on the attempt row of a judged bars attempt (an empty id is NULL, never an empty string; a dropped delivery's row stores NULL, see the stop rule).
- **The stop rule** (`tj-7zjov1.144`, P50, ADR `tj-26jt9w` addenda 12 and 13). In the bars arm, after the entry lock and the drop rule, on every SUCCEEDED bars report that has a dataset (a zero-bar success too), the header's vendor asset id is compared with `last_accepted_vendor_asset_id` (`crud/ingest_run.py`): the newest bars attempt of the dataset (granularity set, so never a corporate-actions row) that is SUCCEEDED or EMPTY and has an id, by `finished_at` then `id`. None earlier or equal: accepted. Different, or empty after a set one: NO BAR is written, the same transaction runs `stop_entry` (`collect` false, `stopped_cause` `VENDOR_ASSET_CHANGED` (`DatasetStopCause`), `updated_at`), the attempt row is FAILED with `error_reason` `VENDOR_ASSET_CHANGED` (`VENDOR_ASSET_CHANGED_REASON`, a run-record marker beside `INTERRUPTED`, `error_domain` NULL, never on problem+json), one sentence naming the symbol and both ids as `error_message`, `vendor_asset_id` the delivered id as received and verdict FINAL; the request is FAILED with cause `VENDOR_ASSET_CHANGED` and the same sentence; one WARNING logs the sentence with the request and dataset ids; `DatasetChanged` `RETIRED` is published after the commit. A refused attempt is never a comparison base, and neither is a dropped one: the drop rule runs before the stop rule, so a delivery dropped for a gone or stopped entry was never judged, and its attempt row (still EMPTY, with its dataset id) stores NULL `vendor_asset_id` (P50f, `tj-7zjov1.163`, addendum 16; the base query is unchanged). So a Resume is a re-check: the next delivery compares against the last accepted id again and stops again on a real holder change. Nothing relabels or moves a bar and no action accepts a new holder into the old series. The refresh's permanence read already ignores the marker (it needs the vendor error domain). A STATIC entry has no collect intent (collect NULL by CHECK, a cause needs collect false): its bars are refused and the attempt and request fail the same way, but the entry is left as it is.
- The lifespan needs both `APP_INTERNAL_GRPC_*` variables; a test that enters it patches `app_depends.build_grpc_host`.

## Seed producer (`python -m data.store.seeds`)

A synthetic-only producer that exercises the store end to end and dumps what it wrote. It POSTs a scenario to data_store (fake bars from the fake-mode data_ingest, written through the push path), empties the tables it will seed, writes a fixed cast through the store's own code (the ingest records, corporate actions, asset lists and the panel cast, in `seeds/ingest_records.py` and `seeds/panel_records.py`, the panel cast through the panel crud with no size and one settings version with a blank reason), normalises what Postgres stamps (`dump.NORMALISE_SQL`), and prints one bundle holding `<revision>.sql` and `<revision>.json`, the data and its manifest (row counts and digests), so two runs give identical bytes. The revision is the checkout's single head, the baseline. **No seed is committed per revision**: there are no committed seeds, no seed gate and no test that loads one; the output is for inspection and as an exercise of the push path and the panel crud.

| Route | What it does |
|---|---|
| `make seed-dump` | Runs the producer in `test_client` against the up, migrated test stack and writes the pair to `SEED_OUT` (default `output/seeds`, git-ignored; the writer refuses to write under `tests/`). Needs `SYSTEM_TEST_DISPOSABLE_DB=1` and a stack from `make system-launch` |
| The agent-stack MCP `seed_dump` verb | The same producer, test mode only; writes under `agent_mcp_seeds/<worktree>/` in the MCP's share directory |
| CI, System Testing job: Seed Dump, then Upload Head Seed | `make seed-dump SEED_OUT=output/ci-seed`, uploaded as an artifact (kept 7 days) so a person can download and inspect it; nothing is committed |

- **It refuses a database holding a real symbol**: only the synthetic names (`ZZSEED` plus letters) and the store's own boot snapshot are accepted, so a suite that left rows behind turns the step red rather than producing a seed from them. Every refusal names counts and cast ids, never a value.
- **The store's own loops can write between the emptying and the dump** (the instance watcher's probe notes the live ingest's instance, which moves a QUEUED cast request to NOT_DELIVERED). The producer therefore judges each cast request by id against its expected state, re-checks the counts and the foreign-row refusal inside one `REPEATABLE READ READ ONLY` snapshot, and on a drift (`CastDrifted`) runs the whole cast again, up to `CAST_ATTEMPTS` (5) times.
- **The dev dataset tool shares its manifest code**: `tools/dev_datasets/dev_seed.py` mirrors `data.store.seeds.manifest.head_revision` and the session options. Dev exports are keyed by the head revision, so exports made before the baseline cannot be loaded into it.

## Usage record (consumption)

Every bar read is recorded as one `dataset_read` row by the usage recorder (`app/usage_recorder.py`): buffered in process, inserted in batches, so the read path issues no INSERT. Rows past the rollup window are folded into `dataset_read_daily` and deleted. Distinct from `ingest_run`, which is collection.

| Concern | Where it lives |
|---|---|
| Tables (no foreign key: usage outlives a dataset) | `app/database/models/dataset_read.py`, `dataset_read_daily.py` |
| Writes, the rollup (one data-modifying CTE) and the usage query helper (`read_dataset_usage`, `read_daily_reads`) | `app/database/crud/dataset_read.py` |
| Buffer, flush loop, rollup loop, stream-session open/close API | `app/usage_recorder.py`, started from the lifespan |
| The reader's label, its kind and `OPERATOR_PRINCIPAL` | `app/client_label.py` |

- **The label is the dataset `owner` string the caller already uses, sent in the `X-Client-Id` header** (tj-grna9p.131). It is self-asserted: a label, never an authority. The `owner` QUERY filter on `/store` GETs is a search filter and is never the label. Missing, empty, over 128 characters, a control character or a leading `_` is `_unattributed`; never truncated.
- **Kind is UI iff the label equals `OPERATOR_PRINCIPAL` (`operator`), else SDK.**
- **At most 32 distinct ids per dataset per UTC day**; later ones are `_overflow`. Applied at flush against the stored ids. The operator and the reserved values are exempt.
- **One read per call** on `GET /internal/asset-data`, per dataset it returned bars of (a query by dataset id that returns none records 0 bars). Listing, metadata, bar-page and coverage reads record nothing. There is no bar GET under `/store`: those routes return dataset entries.
- **Best effort.** A failed flush is logged by type and retried from the buffer; the buffer is bounded and drops its oldest past `USAGE_BUFFER_MAX`. On an unmigrated database one warning names `make migrate` and the rows are dropped.
- **`client_id` is a `SensitiveString`**: never logged, never in a repr.
- **`dataset_read_daily.last_read_at`** keeps the latest read of a folded day, so staleness stays exact after the rows are gone.
- **`GET /ui/v1/datasets/{id}/bars` records one read per call WITHOUT a cursor** (the `X-Client-Id` label; `operator` is kind UI, no header is `_unattributed`); a call with a cursor, and every other `/ui/v1` route, records nothing.
- **Usage on the catalog** (`app/dataset_catalog.py`): `DatasetSummary.usage` on list and detail, the `client_id` (wins, repeatable) / `client_kind` (default SDK) filter, `usage` = `READ_30D` / `STALE` / `NEVER_READ` with `stale_days` (1..3650, default 90, never-read is stale; day-aligned on the UTC date of the last read, stream sessions count, so READ_30D and STALE are complements at 30; the detail route takes the same client filter), `sort=last_read`, and `expires_before` (Expiring Soon: expiry before it, plus the reaper's pending set; ignores the client filter; the facets default it to now + `EXPIRING_SOON_DAYS`). The `owner` query filter is never the reader. Each facet count equals the filtered list's total. The window functions refuse a naive `now`. An unmigrated database reads as zero usage with one warning (`make migrate`).

## Usage statistics (`/ui/v1/stats/...`)

Five open GETs in `routers/data_store/ui_stats.py`, composed in `app/dataset_catalog.py` (`usage_summary`, `last_read_buckets`, `reads_per_day`, `stale_page`, `storage_current`). None records usage; each runs a constant number of statements.

| Route | What it serves |
|---|---|
| `usage/summary?stale_days&source` | `UsageSummary`: stale, read_last_30d, never_read, total, reads_today, distinct_clients_today |
| `usage/last-read-buckets?source` | `LastReadBuckets`: [0,1) [1,8) [8,31) [31,91) [91,open) whole UTC days, plus never_read; sum = total |
| `usage/reads-per-day?days&dataset_id&source` | `ReadsPerDay`: one entry per UTC day, client id and kind, continuous over the rollup |
| `usage/stale?stale_days&source&cursor&limit` | `StaleDatasetPage`: never-read first, then oldest last read, then id; est_bytes and last read per client |
| `storage/current?source` | `StorageCurrent`: the bar table's size, split per (source, feed) as estimates |

- **Every usage route takes the list's client filter** (`UiClientFilterQuery`, `_client_filter`) and echoes it. Storage takes none.
- **`read_within` in `app/dataset_catalog.py` is the one day-aligned staleness rule**: the list's usage filter, the facets, the summary and the stale list all decide through it, so their stale counts agree for one filter.
- **Estimates**: a share is `bar_count * total_bytes // total_bars` (`estimate_bytes`); with a `source` the storage total is the sum of that source's shares, so the split always sums to it. Quota burn is not served (tj-lenn8u).
- **The stale cursor** is bound to stale_days, source and the client filter by a digest, so it carries no client id.

## Operator writes (expiry, collecting and delete)

`PATCH /ui/v1/datasets/{id}/expiry`, `PATCH /ui/v1/datasets/{id}/collecting` (both 200, the updated `DatasetSummary`) and `DELETE /ui/v1/datasets/{id}` (204) are the UI's writes, in `routers/data_store/ui_dataset_writes.py`. All three need the instance secret; bodies are `SetExpiryRequest` / `SetCollectingRequest` / `DeleteDatasetRequest` parsed by `ProtoBody`, with no pydantic model.

| Concern | Where it lives |
|---|---|
| The operator-path writes (`operator_set_expiry`, `operator_set_collecting`, `operator_delete_entry`), beside the owner-scoped ones, which are unchanged | `app/database/crud/stock/store_dataset_entry.py` |
| The override decision, `OverrideRequired`, the INSERTs of the two logs | `app/database/crud/dataset_override.py` |
| Tables (no foreign key) | `app/database/models/dataset_override_log.py`, `dataset_deletion.py` |

- **Rule order** (expiry and delete): 422 bad body, 404 unknown id, 409 `OVERRIDE_REQUIRED` (owner is not `OPERATOR_PRINCIPAL` and the override is missing, unconfirmed or blank; no owner in the body), then the write. An override sent for the operator's own dataset is ignored.
- **One transaction per write**: the write, its `dataset_deletion` row (every delete) and its `dataset_override_log` row (only an override, reason stored trimmed; the log's action is `SET_EXPIRY`, `SET_COLLECTING` or `DELETE`). The `DatasetChanged` event is published after the commit: `UPDATED` after an expiry PATCH, `RETIRED` / `RESUMED` after a collecting PATCH that flipped the stored value, `DELETED` after a DELETE.
- **Both tables are append-only**: never an UPDATE or DELETE. `dataset_deletion.cause` is a string so the reaper (tj-grna9p.23) reuses the table.
- **Setting or clearing an expiry changes only the deletion date**; the expiry type is never writable. The expiry is stored as sent, and a past time makes the dataset reaper-pending, nothing else.
- **`PATCH .../collecting`** takes `{collect, override}`. Rule order: the instance secret; 422 when the body has no `collect` (presence: a missing key is never read as false), before anything else; 404 unknown id; 422 for a `STATIC` dataset (no intent); 409 `OVERRIDE_REQUIRED` for another owner's dataset without a confirmed override; then the write. It publishes `RETIRED` (to false) or `RESUMED` (to true) only when the stored value changed; a repeat of the stored value publishes nothing. The row is locked `FOR UPDATE` to tell a flip from a repeat. Collect true also sets `stopped_cause` NULL in the same UPDATE (a Resume of a store stop); collect false leaves it as stored.
- **An unmigrated database** refuses the audited writes: an overriding PATCH and every DELETE answer 503 `DATABASE_UNAVAILABLE` (detail names `make migrate`; no owner, no metadata) after the 404/409 checks and before any write; an operator-owned PATCH still goes through. One process-wide warning names `make migrate` (`audit_tables_exist`, `AuditUnavailable`).
- **A DELETE may carry no body** (the operator's own dataset needs no override); a body that is sent is parsed strictly.

## Expiry reaper (dry-run by default)

A periodic pass (`app/reaper.py`, the shared `run_periodic` with `Every`, started and stopped in the lifespan beside the usage loops) over the datasets whose expiry has passed. It stores no jobs: catch-up after a restart is the next pass, which reads the database each time.

| Concern | Where it lives |
|---|---|
| The pending-set query (`expiry <= now`), written once: `list_pending` (keyset over expiry, id) and `pending_ids` (all, or those among a page's ids: what `DatasetSummary.reaper_pending` reads) | `app/database/crud/stock/dataset_catalog.py` |
| The pass, the env flags, the events, the loop | `app/reaper.py` |
| The delete (`reaper_delete_entry`, its own transaction, the cascade and record of the operator delete) | `app/database/crud/stock/store_dataset_entry.py` |
| `GET /ui/v1/reaper/pending` (open; `ReaperPendingPage`) | `routers/data_store/ui_reaper.py`, `reaper_pending_page` in `app/dataset_catalog.py` |

- **DRY-RUN IS THE DEFAULT.** `REAPER_DELETES_ENABLED` must be the value `true` (any letter case, surrounding whitespace ignored) to delete anything; anything else, including unset, `1` and `yes`, is dry-run, and the flag is unset in every committed file (pinned by `server/common/tests/test_reaper_deletes_never_committed.py`). The default exists because STATIC rows created under the former now+1-day expiry default are all past expiry: the operator reads `GET /ui/v1/reaper/pending` before anything goes. Dry-run logs a count only, never an owner or a symbol.
- **The reaper deletes at expiry whatever `collect` says.** A Stopped subscription with a passed expiry is pending like any other dataset, and one with no expiry is never reaped.
- **Enabled**: each pending dataset is deleted in its own transaction on its own session, recorded in `dataset_deletion` with cause `REAPER` and actor `reaper`, with NO override-log row (a system action). `DatasetChanged` `DELETED` is published after each commit. A failure on one dataset is logged by exception type only and the pass carries on. The row is read `FOR UPDATE` and its expiry and running-ingest state re-checked under that lock, so a PATCH that extends the expiry either commits first (the dataset is left alone) or waits and gets its own 404. A fetch not yet acknowledged has no dataset id (tj-jc635p) and is not seen: if its dataset is deleted the fetch recreates the entry.
- **A missing audit table means an enabled pass deletes nothing** (one warning, `audit_tables_exist`): a deletion is never unrecorded. Dry-run is unaffected.
- **A dataset with a `RUNNING` ingest is skipped** and retried on the next pass.
- **`ReaperPendingChanged`** is published when the pending ids differ from the previous pass's, after enabled-mode deletions, and once on the first pass after start, in dry-run too. Whether deletions are on is `ReaperPendingPage.deletes_enabled`. The previous ids live in process memory (one worker).

## DAILY refresh (interim scheduler)

An INTERIM store loop (`app/daily_refresh.py`, tj-grna9p.22) that keeps DAILY datasets current. Ingest's scheduler module is built (queue, ready-by check, pacing, acknowledged retry: [`docs/scheduler.md`](../../../docs/scheduler.md)) but it does not generate standing requests, so the loop stays until ingest schedules them (decision `tj-pd41mt`, still proposed); then it is removed. **Since P35 (`tj-7zjov1.28`) the pass WRITES AND SUBMITS one request per owed dataset (trigger SCHEDULE, `dataset_id` set, `ready_by` the next market open, actor `scheduler`) and does not wait for it**: the result is pushed to the delivery intake, which writes the bars; a dataset with an open request is not owed again; `PassResult.refreshed` counts requests submitted and there is no `discarded` count (a dropped delivery is the request's EMPTY / DISCARDED outcome). The paragraphs below describe the pass as it was built; where they say the fetch, the run recorder or `store_market_activity_worker` read the submit path and the intake's arm. One shared `run_periodic` per source in `SOURCE_CALENDARS`, on `AfterTradingEvent(calendar, CLOSE, settle)`, started after the fetch client in the lifespan and stopped before its channel closes.

| Concern | Where it lives |
|---|---|
| The pass, the env, the loops | `app/daily_refresh.py` |
| The request it submits: `submit_bars`, the request path `POST /store` uses, trigger `SCHEDULE`, actor `scheduler`, naming its dataset (`dataset_id`) and the entry's own feed, not awaited | `submit_bars(..., fetch_start=)` in `app/ingest/data_action_request.py`; the result is written by `app/ingest/delivery_intake.py` |

- **The work is read from the database on every pass**, never stored or replayed: DAILY entries that are not retired (`is_retired`: `collect` is false; an expiry alone retires nothing), have no `RUNNING` ingest, and read LATE or OVERDUE under the health rule (last bar before the last completed session). A pass also runs once at start, so datasets requested earlier are backfilled.
- **Only the missing tail is requested** (`_fetch_start` in `app/daily_refresh.py`, tj-7zjov1.114). It starts just after the newest STORED bar, a placeholder (volume 0 and trade count 0) included, so a series the vendor keeps padding is not asked for again from its last real bar on every pass; health, the LATE or OVERDUE selection and the pass order still judge the newest REAL bar. It reaches back, so that no bar can stay stale, to the oldest of: the newest real bar when it is provisional (written before its period closed, `last_bar_is_provisional` in `app/health.py`), and every stored placeholder not yet SETTLED, that is written less than its period's close plus the settle margin plus `PLACEHOLDER_GRACE` (7 days) ago. The vendor's pad may be replaced by real data later; the evidence does not say, so a recent pad is asked for again until it has stood for the grace. Each re-fetch rewrites `updated_at` (the upsert sets it), so a placeholder leaves the window by itself and the window is constant, never growing. A placeholder written long after its close (a backfill) is settled at once. The cost for a dead series is one request per pass for about the grace window (under 10,000 points per call for 1day and for 1min), where it was one call for a tail growing by a session per close. The tail starts from the otherwise computed instant after the bar's period (`_after_bar`): for 1day the next local midnight of the calendar, for 1week the next Monday's local midnight (the week is taken from its Monday, whichever day the vendor stamped), and for 1hour and 1month the fixed step of one bar, because a local-midnight stamp moves an hour between winter and summer and a fixed offset could land past the next bar's stamp. It never starts before the declared start, the declared start is used when there are no bars at all, and a tail that starts at or after the declared end (or now) is not requested (counted as skipped; the end half is a guard, since a DAILY row's declared end does not validate as a request today). **Only a COUNTED bar advances the start** (`_can_be_real`, decision tj-7zjov1.120), because a bar that does not count would pass a session never requested, for good. A bar does not count when it is stamped at or after now; when it was WRITTEN BEFORE ITS OWN STAMP (`written_before_its_stamp`, `updated_at < timestamp`, equality counts: it was a future bar when fetched, so the sessions between that fetch and its stamp were never requested, and with the now test alone it would count once now passes it, leaving a permanent gap after downtime; only a rewrite after the stamp makes it count); when it is outside the declared range `[start, end)`; or, for a PLACEHOLDER, when its period holds no session (a weekend or holiday pad) or the calendar cannot place it. A bar that does not count stays stored, raw, and is ignored by the tail; a real bar (trades) in a no-session period still counts. The cost is a re-request of the sessions before an ignored bar. **Lost anchor:** when the newest real bar exists but does not count, the newest counted real bar (the anchor of the hole check) is unknown. If it fails ONLY by being written before its stamp (inside `[start, end)`, write time known), the tail starts at the local midnight of the period holding its WRITE TIME, or at the oldest unsettled counted placeholder if earlier, never before the declared start: everything before that write was requested by that fetch or an earlier one, and that period is requested whole. This is the normal live 1min case and costs at most one extra session (about 960 bars) inside the call the pass makes anyway. Only a newest real bar outside the declared range or with no write time is the lost-anchor case proper: the newest COUNTED real bar is read (`newest_counted_real_bar`, ONE statement, only then, tj-7zjov1.122) and stands in as the anchor of the run and of the hole check, with its own provisional test, and the tail starts after it as for any dataset; with none (`LostAnchor(None)`) the dataset holds pads only and the tail follows the pads. A direct `_fetch_start` caller that did not do the read keeps the declared start, the full re-fetch the read removes. **A hole inside the trailing run is reached back to** (`_skips_a_period`): if a period holding a session lies between two consecutive bars of the run (the newest real bar, then the pads after it) with no bar of its own, the tail starts after the earlier one, because the vendor padded around a session it never served. Placeholders are read per owed dataset from `recent_placeholder_bars`, newest first, in pages of `PLACEHOLDER_SCAN_LIMIT` (5000) from `PLACEHOLDER_LOOKBACK` before the earlier of the newest real bar's stamp and its write time (before the anchor in the lost case), so a stamp far in the future never leaves unsettled pads unread; the next older page is read only while the page just read ends in an unsettled placeholder, so a dead 1min series is covered however many bars a session holds (extended hours about 960). There is no iteration cap (a cap would silently drop pages); a progress guard raises `RuntimeError` when a full page does not end strictly older than where it began. **A truncated read** (the read stopped on a full page ending in a settled bar, `PlaceholderTail.truncated`) does not pair the newest real bar with the oldest placeholder read: the unread ones between them would look like a hole and the tail would reach back to the real bar every pass, the growing re-fetch this rule removes; pairs among the placeholders read are still checked. **The leading gap is not a hole:** the sessions between the declared start and the first stored bar of a placeholder-only dataset are not re-requested, because the first fetch of any dataset is one write transaction from its declared start, so any stored bar proves that range was requested once and answered empty (decision tj-7zjov1.120; a range answered empty is never re-verified, tj-7zjov1.121). Residuals, accepted: a phantom future bar's written-early floor and its effect on health (tj-7zjov1.172); a placeholder still unsettled but older than the lookback floor (a dataset stopped for months), and one older than a whole page of settled pads newer than it, are not re-asked for. The entry keeps its declared range as identity, so the refresh extends the existing entry; `fetch_start` replaces only the start of the ingest request. The request names the entry's own feed, so the tail is served on the tape the dataset holds (an IEX dataset stays IEX), and a feed the handle cannot serve is a refused ack, never a second entry.
- **Bounded** (the loop is decision tj-grna9p.9 item 1, built under bead tj-grna9p.22; the default of 15000 is a code value set by an owner ruling (2026-11-10), sized for a panel's whole universe of about 14,400 DAILY datasets, and has no decision record of its own; the cap's safety role while no quota is counted per request is tj-pd41mt addendum 4 and gate tj-a4kni8): one dataset at a time, at most `DAILY_REFRESH_MAX_PER_PASS` REQUESTED per pass, per source and across every owner's datasets (skipped datasets do not count). A TRANSIENT failure is logged by exception type only, backs off (doubling, capped at 600 s), and the pass stops after 3 in a row or at once on an error that names `reset_at` (a rate limit). The rest is the next pass's. **No automatic retry by the store** (decision tj-grna9p.55, accepted option B; Retry Now is manual; ingest's own retries inside one request are its attempt budget, `docs/scheduler.md`): a dataset that failed transiently waits for the next session close or the catch-up at start; the backoff only paces the next dataset.
- **Permanent versus transient** is the error vocabulary's own outcome (`REASONS[reason].outcome`, `is_permanent`): REFUSED (a tape ingest cannot serve, an invalid request, a vendor 4xx, own overlap, a constraint violation) cannot succeed on retry; NOT_READY (peer or vendor unavailable, deadline, rate limit, rate budget, vendor auth, 5xx, database unavailable) and an error nobody typed are transient. A permanent refusal neither counts toward the stop nor backs off; it is counted in `PassResult.refused`. A stored row that no longer validates as a request is never sent (`skipped`).
- **Fair, from the database**: the order and the "tried already" state are the history of trigger `SCHEDULE` (`finished_scheduled_runs`, last 7 days), with no job store: the `ingest_run` attempt rows plus the finished SCHEDULE bars requests that are FAILED with no attempt row (a Submit ingest refused for good makes no vendor call, so writes none), read as FAILED with the request's failure cause. Never-attempted datasets go first (oldest newest-bar first), then least recently attempted. A dataset whose last scheduled attempt asked for the same tail and finished EMPTY or as a permanent FAILED since the last session close is not requested again until the next close; once due again it shares the pass with the rest, at most half the cap while others wait. A run that failed before the ack has no dataset id and is matched on symbol, asset type, data type, granularity and requested start; two owners of one symbol with the same tail therefore share that outcome.
- **The refresh never writes a lifecycle field.** Its request names the dataset (`dataset_id`) and records no expiry, expiry type or collect (`carries_lifecycle=False`, `submit_bars`). The delivery intake locks the entry `FOR UPDATE` (`lock_active_dataset_entry`) and writes `updated_at` only (`touch_entry`), so an operator's expiry is never overwritten. A dataset stopped (`collect` set false) or deleted before the delivery landed DROPS it (`DatasetDropped` in `app/ingest/delivery_intake.py`): nothing stored, the request finished EMPTY with cause `DISCARDED`, so an operator's stop is never undone. The drop is the request's outcome; the pass keeps no `discarded` count. POST /store is unchanged: a repeat sets expiry from its body, and leaves collect alone unless it carries one.
- **An unmigrated database** logs one warning naming `make migrate` per process and the pass does nothing.
- **The store counts no vendor quota; ingest paces and counts** (`tj-7zjov1.56`): every Alpaca market-data request takes one scheduler token and is tallied on the attempt (`docs/scheduler.md`), and the tally is the attempt row's `vendor_*` columns. A cumulative cap that survives restarts and admission control are still not built (gate `tj-a4kni8`). What bounds the spend is the cap, the serialisation, ingest's pacing (`ALPACA_RATE_LIMIT_PER_MINUTE`, which may only lower the ceiling of 200) and the missing-tail-only request. Ingest treats a DAILY request as INTERACTIVE priority, the same as a UI request.
- **A fetch not yet acknowledged has no dataset id** (tj-jc635p), so the running-ingest check cannot see a request that is in flight; its bars write idempotently, so the cost is a duplicate vendor call, never duplicate bars.
- **`DAILY_REFRESH_ENABLED=false` is the kill switch** (also `0`, `no`, `off`), read at start: a change needs a restart. The default, and the cap that must exist before a penalising broker is enabled, are in the environment table below.

## Panels and the panel manager

A **panel** is a named, operator-defined selection of one source's assets whose datasets the store creates and keeps (ADR `tj-26jt9w` addenda 20 and 21, epic `tj-7zjov1`). Panels are UI-only (owner ruling 2026-10-27): the tables, the crud, the manager and the `/ui/v1` routes are built, and there is no client or SDK panel API. The messages are `proto/trader_joe/proto/ui/v1/panels.proto`; the web tab is `/data/panels`.

| Concern | Where it lives |
|---|---|
| Five append-only tables: `panel` (name unique, source immutable), `panel_settings_version` (enabled, cadence, allow and deny lists, asset class, exchange, active and tradable filters, and `include_otc`: NOT NULL with no schema default, the crud states it through `DEFAULT_INCLUDE_OTC` = false; `OTC_EXCHANGES` = {`OTC`} names the exchange values it governs, and false with an exchange filter in that set is refused 422), `panel_source_settings_version` (per SOURCE, shared by its panels: `ramp_datasets_per_hour`, `request_cap_per_hour`, the corporate-action window), `panel_pass` (one pass: kind, the settings versions and snapshots it ran under, `dry_run`, `finished_at` and `counts`), `panel_member_transition` (the ledger, with `seq`) | `app/database/models/panel.py` |
| Settings writes: `create_panel` (applies `DEFAULT_PANEL_CADENCE`, MONTHLY, when none is named), `append_settings_version`, `append_source_settings_version`; the reads of the current version | `app/database/crud/panel_settings.py` |
| Ledger: `open_pass`, `append_transitions`, `finish_pass`, `latest_state`, `members_at`, `created_in_window`, `boundary_read` | `app/database/crud/panel_ledger.py` |
| The manager's own reads and its one stop (`panel_entries`, `stop_collecting`, `latest_pass`, `created_requests`) | `app/database/crud/panel_manager_reads.py` |
| The routes: eight reads (R1 to R8, open, no usage recorded) and three writes (W1 to W3, POST, behind the instance secret), served as protobuf canonical JSON; paths in `UiPanelsInterface` and `UiPanelWritesInterface`. Documented in `docs/API.md` | `routers/data_store/ui_panel.py`, `app_endpoints.py`; the view rules in `app/panel_views.py`, the statements in `app/database/crud/panel_reads.py` |
| The manager: pure rules, `PanelManager.tick`, the loop | `app/panel_manager.py`, started in the lifespan after the Submit client, stopped before its channel closes |

- **Append-only, with versions as markers.** A change is a new version row (enable and disable are versions); a version carries `saved_at`, `actor` and an optional `reason` (NULL when none was given; reads map NULL to an empty string). Effective-from has no column: it is the `started_at` of the first non-dry-run pass of that panel naming the version. Only `panel_pass.finished_at` and `counts` are written once after the insert (guarded `finished_at IS NULL`). No foreign key to datasets, requests or snapshots, so a ledger row outlives them. The two hourly rates are OPTIONAL: NULL is NO LIMIT (decision record `tj-2ayia2`, owner ruling 2026-11-07), a set ramp is 1 to int32 max and a set cap 2 to int32 max (a creation costs `REQUESTS_PER_CREATION` = 2 requests; zero is refused by the crud and by the CHECKs `ramp_positive`, `request_cap_min`), and pausing is `enabled` false, never a rate of 0. `current_source_settings` answers None only for a source no panel was created on; the manager's skip for it is a guard.
- **The ledger order.** The newest transition of a member is by `as_of`, then the pass's `started_at`, then the pass, then `seq`, the 1-based append ordinal within the pass that `append_transitions` assigns (`id` is random and `recorded_at` is the transaction start, so a member's `ENTERED` and `CREATED` of one pass tie on everything else). Rows of a dry-run pass are ignored by every read.
- **The writes leave no override-log row and send no event.** `POST /ui/v1/panels` (`create_panel`), `POST /ui/v1/panels/{panel_id}/settings-versions` and `POST /ui/v1/panel-sources/{source}/settings-versions` each append a version row stamped with the operator principal and an optional reason (blank after trimming is stored as NULL; the actor is still required): THE VERSION ROW IS THE AUDIT, so no `dataset_override_log` row is written (addendum 20), and nothing is published on the events socket (there is no panel event type). A create does not start a pass; the manager's next tick runs the first. Every store refusal is `INVALID_REQUEST`, 422, with the store's message.
- **Creation is serialised by name and by source.** `create_panel` takes a transaction-scoped advisory lock keyed on the trimmed name (first), so the loser of two concurrent creates of one name reads the winner's row and is refused as a duplicate, not by the unique index; then the source lock on EVERY create, and reads whether the source has a version under it. A create on a source with NO version ALWAYS writes that source's version 1 from whatever source settings it carries (an absent rate is NULL, an absent window 90 days; none given writes no limits and 90/90), so two concurrent creates write one version 1. It refuses (422, nothing written) **source settings given for a source that already has a version**: a source's settings apply to every panel on it, so they change only through their own write.
- **Transitions** (`PanelTransition`): `ENTERED`, `CREATED`, `DEFERRED`, `REFUSED`, `EXITED`, `DRAINING`, `DRAINED`. A repeated `DEFERRED` with the same cause is not a new row. Causes are free strings pinned by name, no CHECK: `ramp_rate` and `request_rate` (a rate window is full), `clamp_unavailable` (the clamp query failed: the member is DEFERRED, not refused), and, on `REFUSED`, `clamp_window` (the clamped start leaves no window; unreachable while panel datasets are open-ended), `own_overlap` (the owner's own dataset collides) and `vendor_refused` (the creation request finished with PERMANENT failure, so it is not retried while the member stays in).
- **One loop, nothing stored.** `run_periodic` ticks every 5 minutes (`TICK_INTERVAL`, a constant); each tick derives what is due from the rows, so a crash or restart resets nothing. A long `Every` is never used: it would fire on every restart. For each enabled panel of each source with a trading calendar, a failure ends that panel's turn only. Like the other loops it assumes one process: no cross-process lock exists.
- **Two kinds of pass** (`PanelPassKind`). A MEMBERSHIP pass reads the newest ACTIVE snapshot, applies the panel's filters (`row_selected`; with `include_otc` false a row whose exchange is in `OTC_EXCHANGES` is not selected, whatever the other filters say, since the current SIP feed carries no bars for OTC), keeps EVERY match (a panel has no size and no cut), in symbol then vendor asset id order, and decides `ENTERED`, `EXITED`, `DRAINING`, `DRAINED`, `REFUSED`, and for members it creates `CREATED` or `DEFERRED`. A RELEASE pass runs between membership passes, only while the panel's settings version is the deciding pass's, and creates the members whose latest transition is `DEFERRED` while both hourly windows have room; it decides no membership and opens its pass row only at its first transition.
- **The due rule** (`membership_due_at`) counts only FINISHED passes: the due instant is the panel's creation when it has none, else an interval from the last finished non-dry-run MEMBERSHIP pass's `started_at` (MONTHLY: one calendar month, day clamped, `add_calendar_months`; WEEKLY: 7 days; DAILY: the first session close after it plus the settle margin). An UNFINISHED pass (a crash) satisfies nothing and holds the next one off for `UNFINISHED_PASS_RETRY`, one hour, so a pass that crashes every time retries at most hourly; the unfinished row stays as written and one WARNING per such pass names its id. The pass needs an active snapshot at or after the due time (`snapshot_gate`): it waits for one until the next close plus settle, then runs on the older one and logs it. **The first pass runs at creation**, on the newest snapshot without waiting (owner ruling 2026-10-27 (c)); it logs when that snapshot is older than the latest close plus settle.
- **ENTERED is backdated** by evidence (`evidence_as_of`): under the same settings version as the previous pass, a transition is dated at the first snapshot since that pass that shows the new outcome, so a symbol that entered the vendor's list between two passes is dated when it did, not when the pass ran. A settings-driven change is dated by the pass's snapshot.
- **Exits.** A member selected no more whose row is still listed is `EXITED` (a filter exit) and its collecting dataset is stopped (`collect` false through `stop_collecting`, which marks the stop `stopped_cause` `PANEL_MEMBER_LEFT`, the second writer of that column after the stop rule) unless another enabled panel on the source still selects the symbol. A member gone from the list goes `DRAINING` while a panel-owned entry exists for it (`EXITED` when none), and a `DRAINING` member becomes `DRAINED` (entry stopped) once a fetch of the entry has finished since the drain began, or at once when there is no entry. A dataset minted after its member left (its creation request finished after the exit) is stopped by `_late_mint_stops`, only if its request finished at or after the exit, so an operator's later Resume is left alone. `DatasetChanged` `RETIRED` (and `RESUMED`, below) is published at the end of the pass, after `run.finish()`; a pass that raises after an earlier commit of the same pass (the per-member commit in `_create`) has committed its stops and restarts but never reaches the publishes, so those frames are not sent: the datasets are right and a REST reload shows them (accepted residual).
- **Creating a member's dataset** (`_create`). The reserved owner is `panel` (`PANEL_OWNER` in `app/client_label.py`): `POST /store` refuses a body naming it (422), operator writes on its datasets need the override like any other owner's, and it is the `client_label` of the manager's ingest requests. Per member, on the pass's session: existing-entry and in-flight checks, the rate budget, commit; the name_change clamp (`first_request_clamp`) on its OWN session; the own-overlap check with the clamped start; then ONE commit of `ENTERED` + `CREATED` + the bars request row, and the submit after it. The bars verdict is never awaited. **`CREATED` names the REQUEST, never a dataset**: the delivery intake mints the entry on the first delivered attempt, as for any POST, and the dataset is reached through the request row. Within a pass members are created in the selected order (symbol, then vendor asset id), one request each. A rollback in the commit loses that member's rows and the next pass re-decides. The dataset is DAILY, 1day, ROLLING, open-ended, collect true, declared start `panel_dataset_start(source)`: the source calendar's local midnight of `CALENDAR_START` (1990-01-01), never UTC midnight, which would fall on the previous local date before the calendar's first day; a source without a calendar raises `UnknownCalendarError`. The owner has answered whether the start should be a setting: it stays a constant date, kept as the calendar-local midnight. The clamp moves it later.
- **The rate** is per source and per hour, read from the rows each time (a sliding 60 minutes): `created_in_window` (`CREATED` rows) against `ramp_datasets_per_hour`, and `requests_in_window` (every request the `panel` owner wrote, kind and state aside) against `request_cap_per_hour`; a creation costs TWO requests (the clamp query and the bars request). A rate that is NULL (no limit) skips its check. The ramp is checked first. Once a window is full in a pass the rest of the members share its cause. It limits creation only: **the daily bars of members are the DAILY refresh's** (owner ruling 2026-10-31, QR2 option B), bounded by `DAILY_REFRESH_MAX_PER_PASS`, so a source with more collecting DAILY datasets than that cap (default 15000), counting every panel's and owner's, needs it raised by configuration; the refresh loop is interim and moves into ingest's scheduler.
- **Dry run** (`PANEL_MANAGER_DRY_RUN`) writes dry-run passes, whose ledger rows every read ignores: the decisions are recorded, but no dataset is created, none is stopped and no release tick runs. It reads only dry-run passes for its own due rule, so a real crashed pass does not hold a dry-run manager off (the pin is `tj-7zjov1.231`, open).
- **Logs** name ids, counts, sources and exception types, never an owner or a symbol.

### Re-entry

A member that leaves and re-enters keeps its old dataset, because an existing panel-owned entry for the symbol means there is nothing to create (`member_action`). It is **restarted** only when the manager itself stopped it (`collect` false and `stopped_cause` `PANEL_MEMBER_LEFT`; an operator's stop has a NULL cause and the vendor-id stop has `VENDOR_ASSET_CHANGED`, so neither is restarted) and its last accepted vendor asset id is empty or the member's (`_resume_target`; a different id is a reused symbol and the dataset stays stopped). The restart (`resume_panel_entry`, guarded on that same pair so a concurrent operator write wins) is in the same commit as `ENTERED`, whose `cause` is `dataset_resumed` and whose `dataset_id` names the dataset; `DatasetChanged` `RESUMED` is published after the pass, and the DAILY refresh fills the gap on its next pass. `stopped_cause` therefore has two writers and two values: the stop rule (`VENDOR_ASSET_CHANGED`) and the panel manager (`PANEL_MEMBER_LEFT`). `RESUMED` has a second publisher with the same lost-frame residual as `RETIRED` (Exits, above).

## Known limits

Accepted and recorded, not bugs to fix in passing. Each names what bounds it.

| Limit | Detail |
|---|---|
| One usage batch can be counted twice at shutdown | A cancel that lands after the batch INSERT commits but before `flush` returns puts the batch back, so the final flush writes it again. It overcounts usage telemetry by at most one batch, only at shutdown (`app/usage_recorder.py`). |
| About 16,000 datasets per source on the stats routes | The usage and stale queries bind the dataset ids as parameters, and asyncpg allows 32,767 per statement, so a source with more than about 16,000 datasets exceeds it (`tj-ck7blk` replaces the id list with a subquery). |
| The DAILY refresh's skip is shared across owners | The "already tried this tail" rule keys on the identity label (symbol, asset type, data type, granularity and requested start) until `tj-jc635p` gives a fetch its dataset id at request time. Two owners of one symbol with the same tail share a refusal's skip for one session. |
| A dataset resumed after a mid-fetch stop waits | A stop (collect set false) during a fetch drops the answer and is never undone; if the dataset is resumed afterwards, it is refreshed at the next session close, not at once. |
| No automatic retry of a failed refresh | A transient failure waits for the next close or the catch-up at start (decision `tj-grna9p.55`). |
| An unacknowledged fetch has no dataset id | The running-ingest check and the reaper cannot see a fetch before ingest acknowledges it (`tj-jc635p`); a duplicate vendor call is the cost, never duplicate bars. |
| The trading calendars end about a year after the process starts | The store builds each calendar with the library's default end date, so a data_store process that runs longer than about a year without a restart hits an out-of-range error. The DAILY refresh then retries every few minutes without refreshing anything until the process restarts. A follow-up sets an explicit far-future end. |
| The owner string appears in access log lines | The web server logs the raw request path, so `DELETE /store/{id}?owner=...` and `GET /store?owner=...` log the owner from the query string. A follow-up adds a redacting log filter; authenticated per-client keys will move owner off the query string later. |
| The agent-mcp group's `mcp` is capped below 2 | `mcp>=1.30.0,<2` in `pyproject.toml`. Moving to 2.x is the owner's decision. |
| The security tooling group's own advisories are excluded from the audit | That group (semgrep) pins `mcp` 1.29.0 and `pyjwt` 2.13.0, which carry advisories. It is tooling only and in no image, so `make security` does not audit it by design; the findings clear when semgrep raises its pins. |
